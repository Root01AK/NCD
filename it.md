Mumbai’s NCD Survey — Phase II (P2-V6)
Responses to the IT team’s build questions
Each question is repeated as the IT team wrote it, with our response and the reasoning in red below it.
Q1.  Should all these sections be modularised, i.e. each section shows up separately based on the stakeholder, and in chronological order the section completed populates the Participant ID for the next module?
Response:  Yes, modularise it, and yes to auto-populating the Participant ID across modules.
The logic is that this is not one person filling one form; it is six or seven different staff touching the same participant in sequence — field supervisor, nurse, doctor, counsellor, case manager. A single long form on one device would force the participant and the tablet to travel together through the whole camp, which creates a bottleneck at whichever station is slowest, usually the nurse. Modular sections let each station open only its own part on its own device, so the doctor is examining one participant while the nurse screens the next.
The Participant ID must carry forward automatically. If each station re-enters the ID by hand, you will get transcription errors, and a single mistyped digit breaks the link between a person’s vitals and their bloods, which is the kind of error that only surfaces at analysis when it is too late to fix. Auto-population removes that risk entirely.
One condition to build in: a module should open only when the participant record exists (created at the demographics stage), and the linkage module (Section 14) must remain open and editable for up to 45 days after screening, because its three attempts happen long after the camp day. So most modules close on the day, but the follow-up module stays live.
Decision:  Modularise by stakeholder, auto-populate Participant ID, keep the linkage module open for 45 days.
Q2.  Since the nurse has a greater number of activities, will there be more than one nurse at each site? If so, do we need to track based on user ID on the recorded data or input?
Response:  Yes to both. Plan for more than one nurse per site, and yes, stamp every entry with the user ID of the staff member who made it.
The nurse carries eight of the sixteen sections, so a single nurse per site would become the bottleneck the moment throughput rises. Assume at least two nurse stations per busy site and design the module so two nurses can work on two different participants at the same time without collision.
User-ID stamping matters for three reasons. First, accountability — if a reading looks wrong, you need to know who took it. Second, quality monitoring — the turnaround-time report you mention in your third point is only meaningful if it can be read per staff member, otherwise a single slow station is hidden inside a site average. Third, data integrity — if two nurses are entering at once, the user ID is what keeps their records from being confused. Capture the user ID silently in the background; it should not be a question the staff answer.
Decision:  Two or more nurse stations per site; every record silently stamped with the entering user’s ID and a timestamp.
Q3.  TAT (turnaround time) between form completions will be calculated and shared in a separate MIS with management only.
Response:  Agreed, and this is a good idea. Build it, and keep it a management-only view.
Turnaround time between stations is exactly the number that tells you where the camp is jamming and whether you need a second nurse or a second doctor on a given day. Two requests on how to build it so it stays useful. Measure it from timestamp to timestamp between modules (demographics completed to nurse completed, nurse to doctor, and so on), not just total time in camp, because the total hides which station is slow. And keep it strictly a management dashboard, separate from the clinical dataset, so that no one on the floor feels they are being timed on care quality — the moment staff feel watched on speed, they rush the screening, which is the opposite of what we want.
One addition worth making: alongside average turnaround, flag any single participant who spent an unusually long time at one station, because that is often a clinical event (a high reading, a distressed participant) rather than a delay, and management may want to know it happened.
Decision:  Build the turnaround-time MIS station-to-station, management-only, kept out of the clinical dataset.
Q4.  Q27–Q29 (alcohol) are similar to Q21–Q23 (tobacco), but the formatting is not the same. We understand the total score capturing needs to be there. Please check so we can make the changes accordingly.
Response:  Good catch, and you are right that they should behave the same way. Both are scored scales that feed an auto-calculated total, so treat them identically in the build. The only difference is cosmetic and should be standardised.
What is happening: in the tobacco items the score sits in brackets after the option — “Within 5 minutes (3).” In the alcohol items the score is the leading digit — “3 Two to three times a week.” Both carry a score against each option; they just display it differently. Please standardise the display so both show the score the same way, and internally store the score, not the option label, so the totals calculate cleanly.
The mechanics you should build for both:
Scale	Items and range	Auto-calculation rule
Tobacco (HSI)	Q21 (0 to 3) + Q22 (0 to 3)	Sum to Q23, range 0 to 6. Flag ≥ 4 as high dependence; route to counselling (Q111).
Alcohol (AUDIT-C)	Q27 (0 to 4) + Q28 (0 to 4) + Q29 (0 to 4)	Sum to Q30, range 0 to 12. Flag ≥ 4 for men and ≥ 3 for women and transgender; open full AUDIT (Q31–Q32).
So the format difference the team spotted should be resolved by making the alcohol items look like the tobacco items, or the reverse, as long as both display the score against each option and both auto-sum into a read-only total field. The totals (Q23, Q30) are calculated fields, never typed. Please apply the same treatment to the full AUDIT total (Q32) and the two mental-health scores (GAD-7 at Q61, PHQ-9 at Q63), which are also summed scores.
Decision:  Standardise both scored scales to display and store an item score, and auto-sum into a read-only total; apply the same to the full AUDIT, GAD-7 and PHQ-9.
Q5.  Good high-speed broadband is required to carry on the operations smoothly.
Response:  Noted, and largely agreed, but do not let the survey depend on connectivity being good at the moment of screening.
These are community sites — Dharavi, Malvani, Vashi — and mobile data in a dense settlement or inside a chawl will not be reliable all day. If the form needs a live connection to save each entry, a signal drop stops screening and risks losing half-entered records. So the requirement should be built the other way round: the tool must work fully offline and store records on the device, then sync automatically the moment a connection returns. Good broadband at the base or the supervisor’s point is worth having for the sync and for the daily upload, but the field device must never be blocked by a weak signal.
Decision:  Build offline-first with automatic sync on reconnection; treat broadband as needed for sync and reporting, not for screening itself.
Q6.  We will provide a test or demo site so a mock drill can be performed and output extraction can be done and cross-verified before going live.
Response:  Yes, essential. Do not go live without it, and let us cross-verify the extract before the first real participant.
A mock drill is the only way to catch the problems that do not show up on screen — whether the skip logic actually skips, whether the three auto-scheduled follow-up dates land correctly, whether the scores total properly, and whether the exported dataset comes out as clean coded columns with no stray free text. Please run the drill end to end with a handful of dummy participants that deliberately test the edges: one who screens all-negative and should skip large parts, one Red case that must route to referral, one lost-to-follow-up case that exhausts three attempts and must lock, and one self-harm-positive case that must not allow the form to close without escalation. Then extract that data and let us check it against what we expect before sign-off.
Decision:  Mandatory mock drill on the demo site with edge-case dummy records; management signs off on the extract before go-live.
Q7.  If any new questions or sections are to be added, that should be done at the end and not in the middle.
Response:  Understood, and agreed as a build convention — with one caveat about how the participant experiences it.
From a database point of view you are right: appending new fields at the end keeps the variable structure and the existing question numbers stable, which protects any analysis already written against the dataset. So for the stored data and the question codes, add at the end. The caveat is that the participant should still be asked questions in a sensible order on screen — a new diet question should sit with the other diet questions when the nurse asks it, even if it is stored as the last column in the table. Most tools handle this by separating the display order from the storage order. If yours can do that, use it; if it cannot, we will accept end-placement for now and group things properly at the next version rather than disturb a live build.
Decision:  New fields appended at the end for storage and numbering stability; keep on-screen order logical where the tool allows display order to differ from storage order.
Q8.  Response options can be included, as that will not cause an issue.
Response:  Yes, please include all the response options as coded lists exactly as they appear in the instrument. This is the whole point of the version.
Every question in V6 has its full set of coded options for a reason: we have deliberately removed all free text and all “other, specify” boxes, because mixed typed-in answers cannot be analysed and would have to be hand-coded later. So build every option as a selectable code, keep the numbering exactly as written so it matches our codebook, and do not add a write-in box anywhere in the analytic dataset. Where a list ends in a residual option such as “Not stated” or “Cannot say,” that residual is itself a code and carries no text box. The only fields that are not coded options are the genuine numbers (age, height, weight, blood pressure, sugar, haemoglobin) and the dates.
Decision:  Include every response option as a fixed coded list, numbered exactly as in the instrument; no write-in boxes anywhere in the analytic data.
